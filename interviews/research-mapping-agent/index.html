Research Mapping Agent

📋 AI Agent 工程师候选人挑战题 ⏱️ 预计用时 1~3 天 🏢 ColaOS

背景

ColaOS 正在寻找能够把大模型能力落到稳定产品流程里的工程师。这个挑战希望你实现一个 Research Mapping Agent：它能从一段模糊的招聘或调研需求出发，完成信息检索、候选对象筛选、证据归因、质量复核，并生成最终报告。

这不是一道考察“谁的 prompt 更长”的题。我们更希望看到你如何拆解 Agent 工作流、管理中间状态、处理不确定信息，并用工程手段降低幻觉和失败风险。

场景示例

用户说：“我们想找 5 位在 AI Agent / RAG / Claude Code / LangGraph 方向有实战经验的中文开发者，最好有 GitHub、博客或公开项目，适合作为技术顾问或早期候选人。”

→ Agent 解析需求，拆出搜索关键词、筛选条件和评分标准

→ Agent 搜索或读取多个信息源，提取候选人线索和证据

→ Agent 对候选人去重、打分、排序，并标注风险与不确定性

→ Reviewer 检查证据不足、过度推断或重复项，必要时触发补充搜索

→ 最终输出 Markdown 推荐报告和结构化 JSON

任务一：Agent 工作流设计

必做 请设计并实现一个有明确状态流的 Agent 系统，至少包含以下职责：

  • Planner：解析用户需求，提取搜索条件、筛选标准、优先级和风险点
  • Searcher：使用真实搜索或本地 mock 数据，从至少 3 类信息源获取线索
  • Extractor：抽取候选人、技术方向、代表项目、公开链接和证据片段
  • Ranker：对候选人去重、打分、排序，并说明推荐理由
  • Reviewer：检查幻觉、缺证据、重复、过度匹配，必要时触发二次搜索
  • Reporter：输出 Markdown 报告和结构化 JSON

任务二：技术实现

必做 实现一个可运行的 Demo。CLI、Web 页面或 API 任意一种入口都可以。

  1. 用户输入一段自然语言需求后，系统能执行完整工作流
  2. 至少支持关键词检索或向量检索之一；如不能联网，可提供本地 JSON / Markdown 数据集模拟
  3. 每个关键结论都要能追溯到来源，报告中需要体现证据引用
  4. 每一步中间结果需要保存，便于观察、调试和复现
  5. 最终输出一份 Markdown 报告和一份结构化 JSON

候选人信息至少包含

  • 姓名或昵称
  • 技术方向与相关关键词
  • 代表项目或公开作品
  • 公开链接和证据来源
  • 匹配理由、风险或不确定性
  • 综合评分与排序解释

任务三：工程说明

交付时附带 请在 README 或设计文档中回答以下问题：

  1. 你为什么这样拆 Agent 节点？哪些步骤应该确定性执行，哪些步骤交给 LLM？
  2. 哪一步最容易产生幻觉？你的系统如何发现和控制？
  3. 当搜索结果互相矛盾或证据不足时，系统如何处理？
  4. 如果要支持 10 万条候选人数据，你会如何改造检索、缓存和排序？

技术要求

  • 技术栈不限：TypeScript、Python 或其他你熟悉的语言均可
  • 框架不限：可以使用 LangGraph、LangChain，也可以自己实现状态机
  • 模型不限：可使用在线模型、本地模型，或对 LLM 响应进行 mock
  • 数据源不限：GitHub、博客、技术社区、搜索 API、本地数据集均可

加分项

  • Human-in-the-loop：生成联系话术或发送邮件前需要用户确认
  • 二次搜索：Reviewer 发现证据不足时，能自动补充搜索
  • 成本控制：限制 token、限制搜索次数、缓存搜索结果
  • 可观测性：展示每个 Agent 节点的耗时、输入、输出和错误
  • 失败恢复：搜索失败、JSON 解析失败、模型输出不合法时有兜底逻辑
  • 结构化校验：使用 Zod、Pydantic 或类似方案校验输出
  • 简单 UI：展示 Agent 执行过程、中间状态和最终报告

评估维度

维度权重看什么
Agent 架构20%状态流、节点职责、可扩展性，是否避免单条长 prompt
检索与证据20%信息源质量、证据引用、去重与反幻觉设计
抽取与排序15%评分维度是否清晰，推荐理由是否可解释
工程质量15%代码结构、错误处理、配置管理、可运行性
Reviewer 机制10%是否真的能发现缺证据、重复、错误匹配等问题
用户体验10%运行是否顺畅，报告是否清晰、适合实际场景
测试与评估10%是否提供测试样例、评估方法或回归测试
